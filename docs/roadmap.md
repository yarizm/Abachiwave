# Abachiwave 后续开发路径

> 起点以 [`status.md`](status.md) 为准。本文只描述尚未完成的工作、顺序和退出条件。长期产品范围
> 见 [`plans/02-full-product.md`](plans/02-full-product.md)。

## 1. 排序原则

1. 先关闭当前垂直切片的质量、来源和运维门禁，再增加新的生成能力。
2. 先验证用户可确认的结构化资产，再开发不可控、成本更高的最终音频能力。
3. Provider 或模型升级必须用固定数据集和历史报告比较，不能只验证接口成功。
4. 每个阶段同时包含实现、迁移、测试、实机验证、文档和可回滚的提交边界。
5. 不为缺失的模型能力伪造置信度、Stem、局部编辑或质量结论。

## 2. Phase 1：完成 Milestone 10

### 1.1 Audio-to-MIDI Provider 决策

Basic Pitch 的 onset threshold 调参边界已经探完，留出集上限约 0.410，无法靠调参达到 0.50
观察目标；四族纯后处理也已排除（止音变换、单声部消解、音高重指派、f0 引导切分，最佳 +0.002）。
因此本节的重点是
替代 Provider 的同口径比较：

1. 固定默认、稳健调参候选和至少一个替代 Provider。
2. 在相同标准化音频、参考 MIDI、A_max 和容差下比较质量、时延、内存、许可证与部署成本。
3. 对人声、单旋律乐器和复调素材分别报告，禁止用 overall 掩盖类别退化。
4. 每个候选同时报告起音召回与其失败构成（欠切分/未检测/异音高覆盖），以及 no-offset F1 与止音
   缺口。当前约束是起音召回 0.58–0.60；Basic Pitch 止音缺口 0.163，人工标注者之间 0.089。
   `pYIN + 音符分割` 已被否（开发集 0.467/0.332）；瓶颈是音符分割而非 f0 质量，换 f0 估计器无效。
   YourMT3+ 组合方案已在 Vocadito 留出集达到 0.623/0.441（+0.031），是当前最佳候选，但代价是
   RTF 约 36 倍、内存约 3 倍，且仍未达 0.50。该组合按构造只适用于单声部（复调 offset F1 塌到
   0.077），因此显式路由是必需项而非可选项——所需信号已存在（`AudioUploadKind`），缺口只是
   `input_manifest` 未记录它。下一步需要：(a) 一个不在 MT3 训练混合中的器乐数据集以支撑器乐
   路径的绝对比较（NSynth 已确认不在其中）；(b) 在真实目标硬件上确认 RTF/内存是否可接受；
   (c) 决定是否接受"草稿 + 人工校正"定位而不再追 0.50。
5. 若替代 Provider 只改善某一类别，评估显式路由或用户选择；不要静默组合不可追踪的结果。
6. 将正式默认值放入 Provider 配置与 run manifest，旧任务继续按已记录的参数重建。

退出条件：

- regression gate 已版本化，能阻止默认 Provider 对固定数据集明显倒退。
- product release gate 有真实数据和产品依据；未达到时 UI 明确标记“草稿/需人工校正”。
- Provider 名称、版本、参数、输入 checksum、分析范围和输出资产可端到端追踪。

### 1.2 扩大质量与容量证据

1. 扩大 GuitarSet 的演奏者、风格和片段数量，并增加其他许可清晰的乐器数据。
2. 建立短、中、长音频的冷启动、热推理、P95、RTF、CPU 和内存曲线。
3. 测量单并发和受控并发；给出目标机器的 Worker 数、内存余量、timeout 和队列积压建议。
4. 保存失败样例分类：空结果、过分段、漏音、八度、起音、止音和复调分配。

退出条件：

- 每个正式类别都有足够样本和可解释阈值。
- `docs/runbook.md` 给出目标硬件容量建议与故障处理方法。
- CI 使用小型 regression subset，发布评审使用完整数据集，二者职责分开。

### 1.3 真实参考音频分析

1. 为 tempo/beat、key/mode、结构和和弦分别定义真值格式、容差和评测集。
2. 接入真实 `AudioAnalysisProvider` 候选，保留 deterministic 实现作为 fixture/fallback。
3. 校准字段级置信度；Provider 不返回可靠置信度时只显示警告与来源，不伪造百分比。
4. 结构与和弦的应用进入各自版本化资产流程，不继续扩张 SongSpec 的直接写入面。

退出条件：

- 候选字段具有可复现评测、来源和失败语义。
- 用户确认前不会修改正式资产；确认后产生新的 draft/version，并能预览影响。

### 1.4 音频工作区收尾

- 长音频波形缩放、平移、精细选区和 Marker/region 一致交互。
- 低质量或不适用场景提示，例如复调、人声边界不稳定和超长片段。
- 对所有 supported format 验证上传、标准化、试听、分析、转录和下载闭环。

Milestone 10 总退出条件：音频可以“导入 → 定位 → 分析 → 生成候选 → 人工确认 → 形成可追踪
版本”，并且质量限制和容量边界有真实证据。

## 3. Phase 2：Milestone 11——真实 Demo 与局部音频迭代

进入条件：Milestone 10 的参考分析和结构化 MIDI 来源链稳定。

建议顺序：

1. 定义 `MusicGenerationProvider` 的真实候选、成本、许可、超时和内容安全合同。
2. 同一来源生成多个 Demo variant，支持同步 A/B 试听和选择，不自动覆盖当前版本。
3. 将 Marker/region feedback 转换为带来源范围的 Revision 输入。
4. 先验证可追踪的局部重渲染，再引入 Stem；Stem 必须保存模型、版本、参数和源 checksum。
5. 增加失败恢复、预算限制、缓存/幂等和孤立对象清理。

退出条件：用户能比较、选择和回退多个真实 Demo，局部修改不会破坏其他段落或丢失来源。

## 4. Phase 3：Milestone 12——复用与素材系统

建议顺序：

1. Style Profile 与 Lyrics Profile 的版本化 schema。
2. 项目模板、参考素材库、标签、搜索和来源许可字段。
3. 项目复制与“从模板创建”，明确复制和引用语义。
4. 让 Profile/模板进入 Provider manifest，保证历史生成可重现。

退出条件：可安全复用创作约束和参考资产，不通过复制数据库内部 ID 制造跨项目耦合。

## 5. Phase 4：Milestone 13——协作、评审与 DAW 交付

建议顺序：

1. 本地账号、会话和项目级角色；在此之前不开放公网部署。
2. 评论 thread、mention、解决状态和不可变 Review Snapshot。
3. 审批与交付状态机、审计记录和权限测试。
4. DAW 友好的 MIDI、音频、Stem、tempo map 与 manifest 导出。
5. 项目归档导入、schema 版本兼容和备份恢复演练。

退出条件：权限、审计、快照和导入导出均有端到端验证，且旧项目可以可靠恢复。

## 6. 持续性工程工作

这些工作不单独等待某个里程碑：

- 依赖、安全扫描、迁移升级/降级 smoke、备份恢复演练。
- API 错误契约、请求 ID、指标、结构化日志和队列积压监控。
- 无障碍、键盘操作、桌面/移动浏览器回归和性能预算。
- Provider 成本、速率限制、许可证、模型版本和数据保留策略。
- 文档事实源和验证日期维护。

## 7. 暂不优先

- 在音频输入和来源链未关闭前扩张更多最终音频生成入口。
- 为追求演示效果跳过不可变版本、候选确认或 Provider lineage。
- 把完整模型依赖安装进 API/通用 Worker。
- 在没有真实阈值时把“任务成功”或 `passed: true` 宣称为产品质量通过。
